## 왜 만들었나

부트캠프가 끝나고 나서 우리가 어떤 직업을 갖게 될지는 아무도 모른다.
개발에도 프리랜서라는 길이 있는 만큼, 누군가는 "어쩌면 나는 1인 개발이 잘 어울리는 사람인지도 모른다"고 생각하게 될 수 있다.

우리 중 누군가는 프리랜서가 된다. 그래서 도움이 되고 싶었다.

**"내가 프리랜서라면 뭐가 제일 불편할까. 주변에서는 어떤 불편을 얘기했었나."**
이 질문을 따라가서 만든 프로젝트다.

## 1. 문제 정의

### 돈 얘기를 꺼내는 일이 양쪽 모두에게 어렵다

작업이 한창일 때 연락이 온다. "여기 이것만 살짝 바꿔주세요."

프리랜서는 안다. 이건 처음 얘기한 범위가 아니다.
아는데도, **그 말을 꺼내기가 어렵다.**

#### 프리랜서 입장

추가비를 일일이 말해주는 것 자체가 부담이다.

고객은 모아야 하는데, 금액 얘기만 자꾸 하게 되면 클라이언트 입장에서도 외주를 맡기는 데 한 걸음 멀어진다.
프리랜서 입장에서도 금액 얘기만을 하기가 쉽지 않다.
성격 때문일 수도 있고, 고객의 마음을 헤아려야 하니 생각이 많아진다.

> "이것도 추가비인데…" 라는 말을 열 번 중 몇 번이나 실제로 꺼낼 수 있을까.
> 대부분은 그냥 해준다. 그리고 그게 쌓인다.

#### 클라이언트 입장

반대편도 억울하다.

외주는 맡겼는데, 결과물을 받는 마지막 순간에 **슬쩍 추가비를 요구받는 경우**가 있다.
그때는 이미 일정이 코앞이라 거절할 수도 없다.

> "왜 이제 와서 말하지?"
> 사실 프리랜서도 처음부터 말하고 싶었다. 말할 타이밍과 근거가 없었을 뿐이다.

### 그래서 양쪽 다 손해를 본다

| | 지금 벌어지는 일 |
|---|---|
| 프리랜서 | 말 못 꺼내고 공짜로 해준다 → 수익이 샌다 |
| 클라이언트 | 막판에 예상 못 한 청구를 받는다 → 신뢰가 깨진다 |

**이건 둘 중 누가 나빠서 생기는 문제가 아니다. 판정 기준이 없어서 생기는 문제다.**

### 이 도구가 하는 일

사람이 말하지 않는다. **화면이 먼저 말한다.**

클라이언트가 수정 요청을 **제출하기 전에**, 그 요청이 유상인지 무상인지와 그 이유가 화면에 뜬다.
프리랜서는 돈 얘기를 꺼낼 필요가 없고, 클라이언트는 뒤통수를 맞지 않는다.

## 2. 주요 기능

### 핵심 아이디어: 횟수를 세지 말고, 결정을 잠근다

"수정 3회까지 무료"라는 계약은 현실에서 작동하지 않는다.
**이게 수정인지 새 작업인지를 판정할 기준이 없기 때문**이다.

특히 디자인·개발처럼 결과물이 말랑한 분야는, 경계를 자연어로 정의하려 하면 영원히 못 정한다.
그래서 이 도구는 **의미로 판정하지 않고 구조로 판정한다.**

> **유상이냐 무상이냐 = "이미 확정된 결정을 뒤집는 요청인가"**

### 판정 규칙

| 요청이 가리키는 항목 | 판정 | 근거 |
|---|---|---|
| **잠긴 항목** | 유상 | "9월 20일 본인이 승인함" 이력이 함께 표시됨 |
| **목록에 없는 신규 요구** | 유상 | 애초에 계약 범위 밖 |
| **미확정 항목** | **무료** | 작업 전에 물어보지 않은 쪽(프리랜서)의 책임 |
| 확정 전 + 무료 횟수 남음 | 무료 | 정상 범위의 수정 |

세 번째 줄이 중요하다. **이 도구는 프리랜서 편만 들지 않는다.**
확정 항목을 비워둔 채 작업을 시작했다면 그건 프리랜서 책임이고, 나중에 클라이언트가 바꿔도 무료다.
양쪽 다 납득 가능한 규칙이기 때문에 실제로 쓰일 수 있다.

### 기능 목록

| 기능 | 설명 |
|---|---|
| **확정 항목 체크리스트** | 직종별 프리셋 제공. 비어 있으면 빨갛게 표시되고, 다 채워야 승인 단계로 넘어간다 |
| **단계 승인 = 잠금** | 클라이언트가 "1차 검수 승인"을 누르면 그 시점에 채워진 항목이 전부 잠긴다 |
| **제출 전 실시간 판정** | 요청 대상 항목을 고르는 순간, 제출하기 전에 유·무상 판정과 근거가 뜬다 |
| **결정 타임라인** | 승인과 요청이 시간순으로 쌓인다. "그런 말 없었다"가 성립하지 않는다 |
| **직종 프리셋 5종** | 개발 / 디자인 / 영상 / 번역 / 촬영 — 각 직종의 확정 항목이 자동으로 깔린다 |
| **로그인 없음** | 링크가 곧 권한. 클라이언트는 가입 없이 링크 클릭 한 번으로 참여한다 |

### 왜 클라이언트(갑)가 이걸 써주는가

을의 도구를 갑이 써줄 이유가 없으면 제품은 돌아가지 않는다. 그래서 갑에게도 실익을 뒀다.

- **가입 없음, 링크 클릭만** — 진입 비용 0
- **추가비가 붙는 시점을 요청 전에 미리 안다** — 막판에 뒤통수 맞지 않는다
- **내가 뭘 승인했는지 기록이 남는다** — 프리랜서가 말을 바꿔도 근거가 있다

## 3. 시연 경로

미리 채워둔 데이터로 진행한다. (1차 검수 승인 완료, 6개 항목 중 4개 잠김 상태)

1. **랜딩** — 3단계 설명과 예시 판정 카드 (약 10초)
2. **클라이언트 화면** — 잠긴 항목 4개(🔒)와 미확정 항목 2개(주황)를 보여준다
3. **수정 요청에서 잠긴 항목 선택** → 제출 전에 **"9월 11일 1차 검수에서 확정한 항목입니다 · +50,000원"** 배너가 뜬다
4. **미확정 항목 선택** → 같은 자리에 **"무료 수정"** 배너로 바뀐다. 시스템이 프리랜서 편만 들지 않는다는 증거
5. **작업자 화면** — 청구 합계와 결정 타임라인이 자동으로 쌓여 있다

## 4. 예상 반박과 대응

### 핵심 프레임: 기록(record)은 있어도 상태(state)가 없다

구글폼, 노션, 카톡 전부 같은 결함을 공유한다.
응답은 쌓이지만 **"이 항목이 지금 잠긴 상태인지"는 아무도 추적하지 않는다.**
그래서 사람이 매번 스크롤을 올려 눈으로 찾아야 한다.

이 프로젝트는 항목마다 `locked_at`을 들고 있어서, 잠김 여부가 **DB 조회 한 줄**로 나온다.

| 반박 | 대응 |
|---|---|
| **구글폼 체크리스트로 대체 가능하지 않나요?** | 폼은 제출 후에도 계속 수정 가능하고, "승인 시점 이후 잠금"이라는 개념이 없습니다. 응답을 고쳐도 그게 이전 승인을 어긴 건지 폼은 판단하지 못합니다. |
| **카톡 오픈채팅에서 양식을 먼저 주고 클라이언트가 그대로 채워서 답장하는 경우도 있는데요?** | 그 방식도 결국 **텍스트 한 덩어리**로 끝납니다. 항목 6개를 채웠어도 채팅방엔 메시지 하나일 뿐이고, 어떤 항목이 이후 승인으로 잠겼는지는 어디에도 기록되지 않습니다. 결정적으로 그 템플릿은 **프로젝트 시작 시점 한 번**만 채워지는데, 저희는 **1차 검수·2차 검수처럼 진행 중 매 단계마다 항목이 순차적으로 잠깁니다.** 채팅 템플릿은 스냅샷 한 장이고, 저희는 타임라인입니다. 그리고 3개월 뒤 "지원 브라우저 바꿔주세요"가 왔을 때 그게 템플릿의 몇 번째 답변과 연결되는지 채팅방에서 찾으려면 스크롤을 몇백 개 올려야 합니다. |
| **카톡·이메일로 확정받으면 되지 않나요?** | 근거가 있어도 사람이 찾아야 하고, 상대가 "그런 말 안 했다"고 하면 대화 로그를 뒤지는 데 시간을 씁니다. 저희는 그 판정을 자동화해서, 요청 **제출 전에** 화면이 먼저 말합니다. |
| **계약서에 조항 하나 넣으면 끝 아닌가요?** | 계약서는 사전에 고정되지만 실제 범위는 진행되며 매 결정마다 확정됩니다. 계약서는 정적이고, 저희는 결정 단위로 동적으로 잠급니다. |
| **노션으로 문서화하면 되지 않나요?** | 기록은 되지만 판정은 여전히 사람 몫입니다. 매번 재판단해야 하는 걸 시스템이 대신하게 만든 것이 이 프로젝트입니다. |
| **결국 사람이 커뮤니케이션 잘하면 되는 문제 아닌가요?** | 이 문제가 반복되는 이유가 바로 그것입니다. 말로만 하면 항상 작업자가 불리합니다. 근거가 클라이언트 **본인의 클릭**이면 애초에 다툴 여지가 없어집니다. |
| **지라·컨플루언스가 이미 있지 않나요?** | 그건 팀·에이전시용이고 클라이언트는 쓰지 않습니다. 저희는 로그인 없이 링크 하나면 끝이라 클라이언트가 거부감 없이 씁니다. |
| **AI로 요청 내용을 분석해 판정하면 더 정교하지 않나요?** | 의도적으로 쓰지 않았습니다. 자연어 판정은 애매함을 그대로 남겨 분쟁이 재발합니다. **"잠김 여부"라는 구조로만 판정**해서 판정 자체에 대한 다툼을 원천 차단했습니다. |
| **Bonsai 같은 프리랜서 SaaS가 이미 있지 않나요?** | 그런 툴도 수정 "횟수"만 세지, "이게 그 결정을 되돌리는 요청인가"는 여전히 사람이 판단합니다. 저희가 자동화한 건 그 판단 자체입니다. |

## 5. 기술

| 항목 | 선택 |
|---|---|
| 프레임워크 | Next.js 16 (App Router, Server Actions) |
| DB | Supabase (PostgreSQL) |
| 배포 | Vercel |
| 외부 API | **없음** — 판정은 순수 로직, 네트워크 의존 0 |

### 판정 로직

전부 [`lib/judge.ts`](lib/judge.ts) 한 파일, 분기 4개로 끝난다. 자연어 해석이 없다.

```bash
node --experimental-strip-types --test lib/judge.test.ts
```

### 데이터 모델

```
project    프로젝트 (작업자 토큰 / 클라이언트 토큰)
 └ spec_item   확정 항목 (value가 비면 미확정, locked_at이 있으면 잠김)
 └ approval    승인 단계 (이 시점에 채워진 항목이 잠긴다)
 └ request     수정 요청 (어떤 항목을 가리키는지 + 판정 결과 + 근거)
```

### 로컬 실행

```bash
npm install
# .env.local 작성 (Supabase > Project Settings > API)
#   SUPABASE_URL=https://xxxx.supabase.co
#   SUPABASE_SERVICE_KEY=eyJ...   (service_role)
npm run dev
```

Supabase SQL Editor에 [`schema.sql`](schema.sql) → [`seed.sql`](seed.sql) 순서로 실행하면 시연 데이터가 들어간다.
